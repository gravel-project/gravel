# Changelog

All notable changes to gravel are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow
[Semantic Versioning](https://semver.org/), with the 0.x rule in `docs/releasing.md` ("Versions"):
before 1.0, a minor release breaks something a host depends on (its entries say **Breaking:**), and a
patch release is everything else.

## [Unreleased]

### Changed

- **Breaking:** five roles with a game scope (#185, ADR-0027 §3 to §5). Grants replace the moderator role: a member holds admin, operator or moderator, everywhere or for one game.
  - **Bundles:** admin is everything but `org:transfer`; operator is `servers:read|operate|configure|lease`, `events:read`, `stats:read`, `metrics:read`; moderator is `servers:read|moderate|lease`, `identity:read`, `events:read`, `stats:read`; a member keeps `servers:read`. A game-scoped grant gives only the scopable capabilities (`servers:*`, `roles:grant`, `events:read`) for that game's servers, those added later included.
  - **Moved:** park, unpark and the expectation (`SetServerHostDesired`, `SetServerHostExpectation`) need `servers:operate`, not `servers:moderate`. An app holding only `servers:moderate` loses them; give it `servers:operate` (a new app scope). Members' tokens need `servers:operate` for them too.
  - **Migration 00025:** `role_grants`; `role_changes` gains `game_id` and `by_app_id`. Every member who held `moderator` gets a moderator **and** an operator grant, so nothing they did stops working; prune the operator grants on the Members page. `users.roles` is no longer written or read (#199 drops it).
  - **The API:** `SetUserRoleRequest.game_id`; roles `admin` and `operator`; `User.grants` (`RoleGrant`); `User.roles` is the instance-wide grants by name; `IdentityService.ListRoleGrants` (`identity:read`). Who may grant: `roles:grant` for the grant's scope, admin grants by the owner only, an app (new scope `roles:grant`) moderator only, never one's own grants. The audit log and lease list without a server show a game-scoped caller their games' rows. The access matrix carries every change.
  - **The pages:** the Members page lists grants with remove buttons and grants a role everywhere or for one game, for anyone holding `roles:grant`, who also gets the Members link; moderators may read the list.
  - **Docs:** `docs/hub.md` "Roles"; `docs/bot.md` (role sync never grants more than moderator); ADR-0027 accepted, with an as-built section.
- Permissions are checked against **capabilities** (#184, [ADR-0027](docs/adr/0027-capabilities-five-roles-game-scope-and-ownership-transfer.md) proposed; H1, #182). A capability is an `area:verb` name, and app scopes are the same names: every procedure checks one through `internal/authz`, and `api.Access` resolves who is calling (the owner, a member with their roles, a member's token narrowed to its scopes, an app, or nobody). Who may call what is unchanged but for one answer: an app calling `UpdateOrganizationSettings` or `SetUserRole` is told `permission_denied` instead of `unauthenticated`.
  - **The vocabulary:** the seven scopes keep their names; eleven more are named for H1 (`servers:operate`, `servers:provision`, `servers:manage`, `members:manage`, `roles:grant`, `settings:write`, `apps:manage`, `events:read`, `metrics:read`, `stats:erase`, `org:transfer`). An app may hold a capability once a procedure lets an app use it, so `apps create` still accepts the same seven.
  - **The API:** `User.capabilities` in `GetMe`, `ListUsers` and `SetUserRole`'s answer: what the member holds in person.
  - **The access matrix:** `TestAccessMatrix` calls all 57 procedures as 18 kinds of caller and compares the answers with `internal/api/testdata/access_matrix.txt`; a new procedure fails it until it is listed.
  - **Docs:** `docs/hub.md` "Capabilities" replaces "Roles", and its scopes table gains `servers:lease`; ADR-0013 is marked superseded in part.
- **Breaking:** `cloudvm.Game` gains `Exec` (a console command the Game spec names, for a lease's load command and plugin check), and `cloudvm.ServerSpec` gains `ExtraEnv` and `Files` (#20). An implementer of `cloudvm.Game` adds `Exec`.
- **Breaking:** `cloudvm.EnvScript` and `cloudvm.EnvHashScript` take the game's hooks (#170): the push writes them after the environment file, and the hash command prints one SHA-256 per file. The hash the hub records (`server_hosts.env_sha256`) is now the SHA-256 of the environment file's and each hook's SHA-256 in turn, so every cloud-VM server's record differs once: the next time its server is empty, the hub pushes its files again and restarts the game, which is how the hooks first arrive.
- **Breaking:** `cloudvm.Game.Log` returns a `cloudvm.LogResult` (who connected, and the last boundary) instead of the players alone, `cloudvm.RenderEnv` takes the host's size, and `Manager.Resize` takes `pin` (#37). `games/cs2`'s `Change` gains `MapChange`.
- **Breaking:** `cloud.Provider` gains volume snapshots and volumes made from one (part of #166), so a server's volume can start from an install instead of a 73 GB download. New methods: `CreateVolumeSnapshot`, `GetVolumeSnapshot`, `FindVolumeSnapshot` (by name in a region: not found when none has it, invalid when two share it), `ListVolumeSnapshots` and `DeleteVolumeSnapshot`, with the `cloud.Snapshot` type (`SizeGiB` fractional, `MinVolumeGiB` the smallest volume made from it). `VolumeSpec.FromSnapshot` (a `cloud.SnapshotRef`, by id or by name) makes the volume from one; a snapshot in another region, one bigger than the volume and a reference with both or neither field are refused as `cloud.ErrInvalid` before the cloud is asked, and a missing one is `cloud.ErrNotFound`. An implementer of `cloud.Provider` adds the five methods. `fake.Provider.Snapshot()` and its type are renamed `Counts()` and `fake.Counts`, which gains `Snapshots`, and `fake.Provider.SourceSnapshot` says which snapshot a volume was made from. On DigitalOcean volume snapshots need the token's custom scope `block_storage_snapshot` (create, read, delete), not `snapshot`; scopes can't be edited, so a hub's token is replaced, and the live conformance run checks for the scope first. The conformance suite gains a snapshot step and its cleanup deletes the run's snapshots; `dotest` emulates the snapshot routes and `snapshot_id` with DigitalOcean's rules (the snapshot's region, at least the source volume's size).
- The hub host's cloud-init document is split: `internal/vmdoc` renders the shape every VM gravel makes boots with (admin user, the runtime user on the data volume, podman, security updates, a first-boot script), and `internal/hubvm` adds the hub's files to it. The hub's rendered documents are byte-for-byte unchanged.
- `drivers.Factory` returns a `drivers.Driver` (the monitor's and moderation's calls), and `drivers.ExternalReachable` is a `Driver` plus `drivers.Configurer`; `Target` names the server and game, and its `Endpoint` may be empty for a driver that learns its address. `internal/httpx` gains `SetLogPath`, so a handler can redact its own path in the access log.
- The brand kit under `internal/web/static/brand/` is re-vendored with gravel's new one-liner, "Track every game server your community runs, with cross-game stats and one control plane.": the README banners, the link-preview card and the web manifest description carry it, and the README's banner alt text matches.

### Added

  - **Kinds:** `ownership.claimed`; `settings.updated` with the top-level `sections` that changed and `settings_updated_at`; `app.created` and `app.revoked` (from `gravel-hub apps create|revoke`); `app.granted` when a member allows an app or widens what it may do, `app.grant_revoked` when they take it back. 58 kinds now.
  - **Migration 00027** backfills the claim, every app's registration and revocation and the grants members hold, oldest first, marked `"backfilled": true`.
  - **Docs:** `docs/hub.md` "Events".
- The admin dashboard's scaffold at **`/admin`** (#191, [ADR-0029](docs/adr/0029-the-admin-dashboard-is-a-static-client-in-the-binary.md) proposed; H1, #182): a React and TypeScript client of the hub's API in `web/admin/`, built with Vite and embedded in the binary. It signs in with the session cookie (no session sends you to the login and back), shows a demo hub's banner, follows the host's theme in light and dark, polls every 5 s while the tab is visible, and lists the pages your capabilities allow; this first version has the shell and an overview of your roles and capabilities. The fleet, events and the rest follow (#192, #193).
  - **Building the hub needs Node.js** (24, `web/admin/.nvmrc`): `make build` and `make image` build the bundle first (`make admin`). A plain `go build` still works; that binary answers 503 at `/admin` and says so in its log.
  - **Served** under the pages' Content-Security-Policy: the index for every route, hashed assets cached as immutable. `web.CSP` is exported for it, and `web.Handler.Register` takes a `web.Mux`.
  - **Clients** generated from `proto/` by `buf.gen.ts.yaml` (protobuf-es as a pinned remote plugin) into `web/admin/src/gen/`, committed; `make generate` and its drift check cover them.
  - **Checks:** `make admin-check` (ESLint with no `style` prop, `tsc`, Vitest with axe over each route on fake services); CI's new required **`admin`** job runs it, builds the bundle and checks it holds nothing the CSP refuses; `make a11y` scans `/admin` in Chrome after checking it rendered. The publish job and goreleaser build the bundle before the images.
  - **Docs:** `docs/hub.md` "Admin dashboard", `CONTRIBUTING.md`; ADR-0005 amended.
- The events log: one append-only record of what the hub did, read by cursor (#188, [ADR-0028](docs/adr/0028-events-and-notifiers-no-push-to-browsers-in-core.md) proposed; H1, #182). It is what notifiers, the admin dashboard and the CLI will read.
  - **Storage:** migration **00026**, `events`, with a trigger that refuses every change but the prune, and a backfill of `identity_events`, `role_changes`, finished `audit_log` rows and `server_host_events`, oldest first. Each event is keyed by its source row, so nothing is written twice.
  - **Writers,** each in its source's transaction: registrations, links, unlinks, proofs and password links (logins stay out); role grants; moderation and other audited actions with their outcome; a cloud-VM host's transitions, resizes, steps, and a step that starts failing or recovers; leases; a series ending; backups (`backup.failed`, `backup.stale`, `backup.recovered`, from the status file every five minutes).
  - **Kinds:** 52, each with a fixed severity (`info`, `notice`, `warning`, `critical`), in `internal/events`; a writer naming an unknown kind fails.
  - **The API:** `OrganizationService.ListEvents{after_id, before_id, limit, kinds, min_severity, server_id}` → events, `next_after_id`, `head_id`, `next_before_id`; `events:read`, which an app and a member's token may now hold, and a game-scoped holder reads that game's events.
  - **Settings:** `events.retention_days` (400; 30 to 3650), pruned with the sessions.
  - **Metrics:** `gravel_events_total{kind}` on the hub dashboard's new Events row.
- Password links: staff give someone a local account, and a forgotten password a reset, with a one-time link (#187, ADR-0026). It is how a hub with registration closed gets members, and how a hub with no provider gets its first owner.
  - **The API:** `IdentityService.CreateLocalAccount{username, email}` and `IssuePasswordReset{username}`, behind `members:manage` (the owner, in person), each return a `PasswordLink` (`url` on `auth.base_url`, `purpose`, `expires_at`); `failed_precondition` when local accounts are off. The access matrix gains both.
  - **The host:** `gravel-hub users create-local --username NAME [--email ADDRESS]` and `gravel-hub users reset-password --username NAME`, with no API credential.
  - **The page:** `/auth/local/reset/{token}` sets the password once, within the hour, clears a lockout, ends every session the member had and logs the browser in. The token is never logged (the access log says `<redacted>`), and the page sends `Referrer-Policy: no-referrer`; a page that sets its own referrer policy now keeps it.
  - **Storage:** migration **00024**, `password_links` (the token's SHA-256, purpose, who issued it, expiry, use); a newer link for an account deletes its unused ones; links go with their identity and are pruned 30 days after they expire. Identity events `password_reset_issued`, `password_set`, `password_reset`.
  - **Metrics:** `gravel_password_resets_total{result}` (`issued`, `used`, `invalid`, `refused`) on the hub dashboard's Login row.
  - **Not yet:** mailing a reset link to a recovery address waits for the email notifier: #234, after #196.
- Local accounts: a username and a password are one more way in (#186, [ADR-0026](docs/adr/0026-local-accounts-a-username-and-password-are-a-provider.md) proposed; H1, #182). A hub with no Discord application can have members and an owner.
  - **Config:** `hub.yaml` `auth.local.enabled` (off by default); `config check` names it.
  - **Settings:** `local_accounts` in the Organization settings: `registration` `closed` (the default) or `open`, and `min_password_length` (12 by default, 8 to 128); `LocalAccountsSettings` in the API; `settings check` says them.
  - **Accounts:** the identity `("local", <username>)` with its credential in migration **00023**, `local_credentials`. Usernames are 3 to 32 of `a-z 0-9 . _ -`, compared after NFKC and lower case, with reserved names. Passwords are NFKC, at least the host's minimum, never the username, hashed with argon2id (19 MiB, 2 passes, 1 lane; rehashed at the next login when the parameters change).
  - **Pages:** a username and password form on `/login` (first when the browser last used it: the `gravel_last_provider` cookie); `/auth/local/register` when registration is open; "Log in with a username and password too" on the account page (`POST /account/local`).

  - **Tests:** hashing and rehash, usernames, the one answer, the lockout growing and clearing (fake and Postgres), registration closed and open, a password beside Discord, unlink, a local-only hub offering the form, the rate limit, the settings, and axe over the three new forms.

- Server leases (#20, ADR-0023): an app or a moderator takes a leasable server for a match, with its own password, settings, plugin set and match config. The hub starts the server, says when it is ready, and parks it and gives it back after. It is the transient-server API, with a standing cloud-VM server, or a pool of them, as its first provisioner; a fresh VM per lease is #177 and Agones is K1.
  - **`servers.yaml` `vm.lease`:** `pool`, `release_after` (5m), `idle_after` (15m), `max` (4h), `ready_within` (15m), and the `settings` a lease may set, each checked.
  - **`ServerLeaseService`:** `RequestServerLease` names a server or a pool and the holder's reference: one live lease per server and per reference, and asking again answers it. The hub takes a running empty server first, then a parked one, never one with players on. The answer holds the join password and connect line. `GetServerLease` and `ListServerLeases` read leases (an app sees its own), `ReleaseServerLease` gives one back, and `WatchServerLease` streams it at every change with a heartbeat every 30 s until it is over (the hub's first server stream). Callers are an app with the new scope `servers:lease`, or the owner and moderators in person; never a member's token. Every request and release is an audit row (`lease_request`, `lease_release`).
  - **The password is derived, never stored:** an HMAC of the lease's id under the new `hub.yaml` `leases.key_file` (`GRAVEL_LEASE_KEY`). Without a key the hub leases nothing, and `config check` says so.
  - **How it reaches the server:** a live lease is an overlay on the spec the cloud-VM Manager reads (password, settings, the plugin set's environment, the match file), so the environment push and drift repair carry it, and the Manager reads the specs again as a lease starts or changes. A lease is ready once the host runs its environment (`Manager.EnvCurrent`), the game answers, its plugin set answers the Game spec's check, and its match config is loaded (`Manager.Exec`). Its `expected_players` become the server's expected population (#172).
  - **Ending:** `release_after` after the match's series ends, `idle_after` empty once ready, `max`, a park, the server leaving the manifest, `ready_within` without getting ready (failed), or a release. The expectation is cleared and the server parks; its own password and settings come back at its next start.
  - **The page:** the server's machine panel lists its recent leases, with "Give back the lease" for a live one, through the confirmation.
  - **Store and metrics:** migration **00021** adds `server_leases`; `gravel_leases_total`, `gravel_lease_plugins_total`, `gravel_lease_ready_seconds` and `gravel_leases_live` are on the hub dashboard's new Server leases row.
  - **Tests:** a lease from request to ready with its password and settings in the game's environment, asked again, a second reference refused, released with the server's own spec back, released twice; every refusal with no row left; plugins and a match loaded; the vanilla fallback; ending by idleness, the match's end, the most and a park; never ready; a restart mid-lease; watching; the callers; the rows on Postgres; and request, watch to ready, refusal and release end to end on Postgres.
- A pinned plugin channel on the cloud-VM path (#176). A Game spec's `cloudvm.lease.plugins` are pinned sets a lease may ask for; Counter-Strike 2's `matchzy` is Metamod:Source 2.0.0.1476 and MatchZy 0.9.1 with CounterStrikeSharp, by URL and SHA-256.
  - **`pre.sh` installs them:** fetched into a cache on the volume (`~/cs2/.gravel/plugins`) and checked, unpacked when the pins change, `gameinfo.gi` patched at every start (SteamCMD rewrites it), and MatchZy's config written with the hub's event and demo routes and the feed token as a bearer header that never reaches the output. With no set asked for, Metamod is stripped and the server is vanilla. Every failure (a bad SHA-256, a failed download, a value MatchZy's config can't carry, a `gameinfo.gi` without its anchor) runs the server vanilla, and `~/cs2/.gravel/plugins.status` says why. The hook runs in a subshell, so nothing it does stops the server starting.
  - **A set that doesn't load** within three minutes of the game starting is dropped: the server restarts without it and the lease goes ready vanilla, `plugin_state` `vanilla` with the reason.
  - **Tests:** `pre.sh` under bash against a fake install served by a test server: install and patch, idempotence and no second fetch, `gameinfo.gi` rewritten and patched again, config lines kept and replaced, vanilla, ten fallbacks, a corrupt cache, curl and no fetch tool, and masking; the profile's plugin checks.
- Proof of control in game (#5, ADR-0022): a member proves an account by typing a one-time code in a game server's chat, where the server's log names the account that typed it. It works where a provider has no sign-in the hub can use, and it proves an existing link again.
  - **The code:** eight symbols of Crockford's base 32 from `crypto/rand` (40 bits), shown once as `7K3M-9QXA` and stored as its SHA-256. It is good for ten minutes and once, bound to the member, the server and, when proving an account again, that account. A new code replaces the open one. Typed as `!link CODE` or `.link CODE`, in any case, with or without the hyphen, from any team or none.
  - **The link rules don't change.** One transaction locks the proof and the account. The account is then linked (event `linked`), proven again when it is the member's (verification method `game-chat`, event `proven`), or, when it is another member's, left alone with the code spent. Every other failure has one answer, "unknown or expired", so a guess learns nothing.
  - **Limits:** five codes per member an hour; codes presented, ten per account and server and sixty per server, every ten minutes. A failure is answered in chat at most once a minute per server. `ratelimit.NewEvery` serves rates slower than one a minute, and a slow bucket is no longer swept before it is full again.
  - **The interface:** `internal/identity/proof`. A `Channel` that a server pushes evidence to (`GameChat`, now) and a `Checker` the hub asks (an RSI bio or PUBG's custom matches, P5: hidden-token-gaming/htg#40, #41). `prooftest` holds the fake store and the conformance suite that the fake and Postgres both pass.
  - **The chat:** `games/cs2`'s roster reads `say` and `say_team` (`Change.Said`), from players cs2log reads only on CT or T as well as spectators and the team-select screen, and drops bots and the console. `cloudvm.LogResult.Chat` carries the lines and `Manager.SetChatSink` hands them to the hub, which answers through `Manager.Say`. - A host's own app scopes, `host:<name>[:<more>]` (John, 2026-10-10; ADR-0008 amendment). A host's service beside the hub (hidden-token-gaming's Muster: `host:muster:read`, `host:muster:write`) can have the hub grant, issue and introspect scopes of its own.

- Members sign in to first-party apps with the authorization-code flow, and apps verify tokens by introspection (#6, ADR-0015, now accepted).
  - **What:** OAuth 2.0 authorization code with PKCE (`S256` only, required for every client), not OIDC: no ID token, no signing key. An app's pages send the member to `GET /oauth/authorize`; the app learns who signed in from `IdentityService.GetMe` with the member's token. First consumer: Muster (hidden-token-gaming/htg ADR-0002).
  - **Registration:** `gravel-hub apps create … --redirect-uri URL` (repeatable; https, or http on 127.0.0.1, `[::1]` or localhost; compared as exact strings); `apps list` shows them.
  - **Authorization endpoint:** a page of the hub. An unknown or revoked client, or a redirect URI the app did not register (close is not enough: a trailing slash, another port, http for https, an extra query), shows an error page and never redirects; any other refusal goes back to the app with `error` and its `state`. Codes are hashed, single use and live 60 seconds; a code presented twice revokes every token issued from it. Members' tokens are opaque, hashed rows of `app_tokens` with the member's id, scopes no wider than the app's, one hour, no refresh token.

### Added

- ADR-0008: gravel's Discord features run as a separate bot process built from public `discord/` packages (`cmd/gravel-bot` the stock binary, a host's binary beside it), services call the hub with client credentials (the slice of #6 the bot needs: registered apps, short-lived bearer tokens, an app principal with scopes), the Discord guild and role mapping lives in the Organization settings and is applied from the manifest, role sync is a reconciler, and Linked Roles metadata is written by the hub's own verification flow without storing a token (#15).

A host's bot imports the same packages and registers its own modules beside the stock ones. The compose stack gains a `bot` profile, the quadlets `gravel-bot.container`, the release the `gravel-bot` binaries and image, `make build` the binary and `make bot-image` the image; `docs/bot.md` is the operator reference. disgo v0.19 is the Discord library.
- Role sync and Linked Roles (#15, ADR-0008 §3–§4). The Organization settings gain a `discord` section (proto `DiscordSettings`): the guild, a `linked` role for a member with any account besides Discord, a role per provider, and `recognition` roles for the first N members by registration, validated like the theme (snowflakes as quoted strings, known providers and rules, no role mapped twice, never `@everyone`, at most 10 recognition entries) and applied from the same manifest; `settings apply` names the mapping in its summary. `discord/modules/rolesync` is the reconciler: each pass reads the mapping, every hub member and every guild member, and adds or removes only the roles the mapping names (recognition roles are added and never removed, bots and unmapped roles are never touched), at start, every `role_sync.interval`, and as soon as the identity log shows a registration, a link or an unlink or a member joins the guild; a role above the bot's is logged and skipped, a member who left is skipped, any other failure ends the pass and the next one retries; `role_sync.dry_run` logs the changes and makes none; `gravel_bot_rolesync_*` metrics. `discord/modules/linkedroles` puts the Linked Roles metadata schema (`steam_linked`, `xbox_linked`, `rsi_linked`, `pubg_linked`, `supporter_tier`) on the application at start, only when it differs, retrying while Discord is away. The hub's `GET /auth/discord/roles` is the application's Linked Roles verification URL: a login that asks for `identify role_connections.write` and writes the member's role connection (the organization as the platform, a 1 for each provider they linked) with the token in hand, storing none (migration 5 admits the `roles` attempt intent); the account page offers to update it after a link or an unlink. `discord/rolemeta` holds the schema both sides use. `ListIdentityEvents` returns the log's `head_id`, where a reader that just made a full pass starts. `gravel-bot config check` reports role sync and Linked Roles; `cmd/gravel-bot` has tests.

### Added

The hub exposes `gravel_backup_last_success_timestamp_seconds`, `gravel_backup_last_run_timestamp_seconds`, `gravel_backup_last_run_ok` and `gravel_backup_status_readable` from the status file (`backup.status_file`) and `gravel_wal_archived_total`, `gravel_wal_last_archived_timestamp_seconds`, `gravel_wal_archive_failed_total`, `gravel_wal_last_failed_timestamp_seconds` and `gravel_wal_archiver_readable` from `pg_stat_archiver`. The layout has a skip link, landmarks and labelled forms; `make a11y` runs axe (`@axe-core/cli` 4.13.0 through npx, driving Chrome) over the login page and fixtures of the account and error pages, and CI runs it as the `a11y` job. `gravel.hub.v1.IdentityService.Logout` ends the calling session and clears its cookie, so the header's logout is an API call too.

## [0.2.0] - 2026-10-09

### Added

- Login (#13): a member signs in with Discord and links Steam, through Goth, on the `(provider, subject)` identity model. New tables for users, identities, an append-only identity log, sessions and attempts in progress (migration 2). Sessions are server-side: an opaque token in an `HttpOnly`, `SameSite=Lax` cookie (`Secure` and `__Host-` behind HTTPS), its hash in Postgres, no signing key; `auth.session_ttl` bounds them. Every login or link is an attempt bound to the browser by a cookie and to the provider's callback by a state value (OAuth2's `state`, or Steam's signed `return_to`), consumed once, so a replayed or forged callback is refused; a link must finish in the session that started it; an identity another member holds cannot be linked; the last identity cannot be unlinked. Pages at `/login` and `/account` (plain `html/template`, a strict CSP, no script; #14 restyles them) with the flows under `/auth/{provider}/start`, `/auth/{provider}/link`, `/auth/{provider}/callback`, `/auth/logout`, `/account/unlink` and `/account/claim`; state-changing forms carry a per-session CSRF token and `net/http`'s cross-origin protection fronts everything. `gravel.hub.v1.IdentityService` (`GetMe`, `UnlinkIdentity`, `RevokeSessions`, `LookupUser` for role sync, owner only until #6). Rate limits per client IP on anonymous requests and per user on authenticated ones (`rate_limit`, 429 with `Retry-After` on pages, `resource_exhausted` on procedures, probes exempt), with `server.client_ip_header` for a trusted proxy. Configuration section `auth` (`base_url`, `session_ttl`, `attempt_ttl`, `discord`, `steam`), the secrets `GRAVEL_DISCORD_CLIENT_SECRET` / `auth.discord.client_secret_file` and `GRAVEL_STEAM_API_KEY` / `auth.steam.api_key_file` with the database URL's precedence, and `gravel-hub config check` naming the providers. Metrics `gravel_auth_completions_total{provider,intent,result}` and `gravel_rate_limited_total{scope}`. Expired sessions and attempts are pruned every ten minutes. ADR-0004 records the decisions.

### Changed

- `ClaimOwnership` needs a session and records the caller as the owner (`Organization.owner_user_id`); the account page carries the claim form (ADR-0002 left the column for this). A claim made by 0.1.0 bound nobody, so migration 2 reopens it and the hub mints a fresh token at its next start (#13).
- Goth's Discord token exchange and Steam profile fetch are done in gravel: the first ignores the provider's HTTP client (no timeout, untestable), the second uses plain `http://` with the API key in the URL and fails without a key. Goth still builds the auth URLs, verifies the OpenID assertion and reads the Discord profile (#13).

### Fixed

- `go.mod`'s `toolchain` moves to Go 1.26.9 (the `go` directive stays 1.26.0): govulncheck flagged GO-2026-6617 in `net/http` at 1.26.8 (reached from the hub's server, the health check and pgx), which turned every PR's `vuln` job red until the toolchain moved. `actions/setup-go` installs exactly the version `go.mod` names, so the bump is the fix.
- `deploy/quadlet/gravel-hub.container`'s health check is the exec form: the string form runs through `/bin/sh -c`, which the distroless image lacks, so podman reported the hub unhealthy while it served fine (found on Hidden Token Gaming's first converge) (#33).

### Added

- `docs/adr/0003-cloud-vm-driver-behind-a-cloud-provider-interface.md`: a fourth lifecycle driver, cloud-VM, for a virtual machine gravel creates, sizes, parks and destroys through a `cloud.Provider` interface that DigitalOcean implements first and AWS, Azure and Google Cloud can implement later; the game under systemd from cloud-init, controlled over RCON and log push; the install on a detachable volume with the root disk minimal and fixed so a resize never touches disk; a vertical scaling policy that walks a tier ladder only at a map change or match end, with hysteresis, a cooldown and a chat warning, in-place first and replace later; parking as a provider-dependent step (a powered-off Droplet bills in full); a minimal DOKS cluster as the operator path's environment with Kind in CI; and the ownership boundary with an operator's infrastructure code (`Adopt`). Decided by John for Hidden Token Gaming on 2026-10-08; the work is #35, #36 and #37 (#34).
- `deploy/README.md` and `docs/hub.md` say the config file must be readable by uid 65532, the container's user: a 0600 file owned by the login user is "permission denied" from inside a rootless container, which cost Hidden Token Gaming's first converge (#32).
