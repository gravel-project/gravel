# gravel — context for Claude Code

## What this is

An open-source framework in Go for hosting many game servers across many games with one control interface and cross-game stats. The hub is one Go service beside Postgres; Kubernetes (the operator plus Agones) is the fully managed driver, added with the first managed game. Design is **complete** as of 2026-09-25 and the build order was revised by `docs/adr/0001-hub-first-kubernetes-later.md` on 2026-10-08 (hub first, Kubernetes later). The hub skeleton (#12), login (#13, ADR-0004), the UI skeleton (#14, ADR-0005), backups (#28, ADR-0006), the Organization settings (#7, ADR-0007) the Discord bot with service credentials, role sync and Linked Roles (#15, ADR-0008) the War Dogs client with its per-build fixtures (`games/wardogs`, the first step of ADR-0010) the servers as hub resources with the War Dogs driver, a poll per server and the status API (`internal/servers`, `drivers/`, `internal/jobs`, ADR-0010's second step) moderation with the append-only audit log (`ModerationService`, ADR-0010's third step; moderators are a hub role the owner grants, ADR-0013), the build watcher, configuration plan and apply with the hub-owned ban list (`ServerConfigService`, ADR-0010's last step), and members signing in to first-party apps with the authorization-code flow and introspection (#6, ADR-0015) are in: `cmd/gravel-hub`, `internal/{config,store,org,identity,session,apps,ratelimit,api,web,httpx,hub}`, `proto/` with generated `gen/`, `deploy/` (compose + quadlets). `docs/hub.md` says how it runs; `make check` is the pre-PR gate. `docs/adr/0003-cloud-vm-driver-behind-a-cloud-provider-interface.md` (2026-10-08) adds the cloud-VM driver: a VM gravel owns through `cloud.Provider`, DigitalOcean first, with vertical scaling at a map change. `docs/adr/0020-the-hubs-own-host-made-by-the-cli-through-the-cloud-provider.md` (2026-10-11) puts the hub's own host with the `gravel` CLI (`gravel hub create`, never a `ManagedServer`); the interface, its fake and conformance suite and DigitalOcean (#35) are in with it (`cloud/`, `cmd/gravel`, `hubvm/`). The cloud-VM driver (#36, ADR-0003 as built) is in: the hub makes, parks, resizes and destroys a Counter-Strike 2 server's VM itself (`drivers/cloudvm`, `games/cs2`, `internal/vmdoc`, `ServerHostService`), with its vertical scaling policy (#37: a ladder walked one rung at a time at a map change, a match's end or an empty server, `drivers/cloudvm/scaling.go`). `docs/adr/0025-hub-as-a-product-the-unplug-test-tiers-and-personas.md` (2026-10-13) frames **H1, hub as a product** (#182): gravel owns the truth and stands with no Discord, Steam or cloud configured; the unplug test (`make unplug`, #198) is the gate; three personas at four deployment tiers (`docs/tiers.md`) are the acceptance criteria; ADR-0026 to 0036 land with their H1 issues.

**Read `README.md` first** — it is the distilled design and the source of truth for every architectural decision. The full block-level design doc with the reasoning behind each decision is at https://claude.ai/code/artifact/e559420c-d087-4f74-8829-853cafbb5eb8 (private).

## Non-negotiable principles (honor these in every change)

1. **Don't reinvent the wheel.** Build on Goth, Agones, SPIFFE/SPIRE, CloudNativePG, TimescaleDB, Connect/buf, OCM, LinuxGSM, goreleaser/cosign. If you're about to hand-roll something one of these does, stop.
2. **Every seam is a provider behind a Go interface**, written in domain terms, with a boring default implementation. Never leak a specific backend's features into an interface.
3. **API-only clients.** CLI and web UI talk to the core API, never to Kubernetes or Postgres. Business rules live in the API exactly once. Resources live in the hub's database; Kubernetes is a driver target (ADR-0001).
4. **The CLI consumes the HTTP-JSON side of Connect, never gRPC.** No gRPC stack in the CLI binary.
5. **Stats events are keyed by provider identity (Steam ID), never internal user ID; identity → user is resolved at read time.**
6. **Game-server logs are authoritative where logs exist.** The ingestion pipeline is reliable delivery on top; where there are none, reconcile against polled state and record gaps explicitly (ADR-0011).
7. **Spokes must keep working when the hub is unreachable.**
8. **The agent never auto-updates and only does what the member-approved Game spec allows.** The hub cannot widen its powers.
9. **The hub owns the truth; its own web UI is the authoritative admin surface. Discord is the golden path, not a requirement:** it mirrors the hub's events and actions behind the same seam as every integration (ADR-0025).
10. **Anonymize, don't delete.** No hard deletes of identity-linked data; tombstone + irreversible re-key.
11. **Trust is not retroactive.** Promotion to Official counts from the promotion timestamp forward.
12. **Per-game operational concerns live in the `Game` spec, never in the core.**
13. **The glue, not an add-on.** With no Discord, Steam or cloud configured gravel still stands up, gets an owner, shows what is wrong and lets them act (the unplug test, ADR-0025). A feature that needs Discord is a bot module over a hub capability that works without it.
14. **Native spine first, plugins second.** Identity, notify-and-respond and permissions are gravel's own; an integration maps onto them, never the other way round.
15. **An old-school floor.** A solo operator with local accounts and a few internet-connected servers for an old game is a supported host; the single-machine tier always stays viable.
16. **Lightweight open source everywhere.** The lightest open-source tool that does the job, at every mechanism.

## Vocabulary (use these names exactly)

- `ManagedServer` — our CRD for one server (NOT `GameServer`, which is Agones').
- `Game` — per-game spec CRD; also a declarative YAML manifest.
- `location` — where a server runs (a cluster, a cloud VM gravel made, a member's PC). Every server has one. A cloud-VM server's names one of `servers.yaml`'s `locations` (a provider, a region, a token file).
- `organization` — on every top-level object; single-tenant today, defaults to the built-in org.
- Trust levels: **Official** / **Community**. Curation states: submitted → approved → featured → revoked.
- Drivers: fully managed (Agones) / cloud-VM (a VM gravel creates, sizes, parks and destroys through `cloud.Provider`; ADR-0003) / external-reachable (RCON, SSH) / externally referenced. Local-execution driver has container (Linux) and native-process (Windows/bare) flavors. Every driver declares a capabilities flag.
- Hub / spoke / agent. Agents dial **outbound**.
- Tiers (ADR-0025, `docs/tiers.md`): a single machine (quadlets) / Compose on a cloud box (#210) / a cloud VM the CLI makes (ADR-0020) / a Kubernetes cluster (K1). Personas: **Neckbeard** (single machine, no Discord, local accounts, the CLI and the API), **VPS Dad** (Compose on a cloud box, wants a dashboard, no cluster), **K8s bro** (a full cluster, every integration, GitOps). A change works for all three or says which one it is not for.

## Stack

Go · Connect (buf) · Postgres (identity and stats; TimescaleDB as an extension on a measured signal, ClickHouse later, behind the stats-store interface) · Goth · templ + htmx (member pages) · React + TypeScript + Vite + Tailwind with Connect-Web (the admin dashboard, ADR-0029) · Discord bot modules (disgo) · podman quadlets as the first deployment target · controller-runtime/kubebuilder + Agones for the fully managed driver (in-cluster only, with Counter-Strike 2; Kind for its e2e, OpenShift supported via Helm + OLM) · SPIFFE/SPIRE + mTLS from the first spoke · the clouds' own SDKs (godo first) behind `cloud.Provider` for the cloud-VM driver, a minimal DOKS cluster as the operator path's environment with Kind in CI (ADR-0003) · Patreon (pluggable payments) · Apache 2.0.

## Build order

Per ADR-0001 (hub first, Kubernetes later) and ADR-0025 (H1 before the operator):

1. Hub: Connect API, Postgres with migrations, config, health, metrics, UI skeleton, podman quadlets
2. Identity: Discord and Steam login, `(provider, subject)` identities, sessions
3. External-reachable driver + War Dogs adapter, stats store, boards, moderation with an audit log
4. Composable Discord modules, OIDC for first-party apps, the participation API
5. `gravel` CLI: first `gravel hub`, the hub's own host through the cloud provider interface and its DigitalOcean implementation (ADR-0020); the thin HTTP-JSON client (`gravel login|logout|whoami|claim|fleet|servers|events`, and the admin commands `members|owner|users|apps|settings|stats|notifiers`, ADR-0031), including `gravel claim`, which consumes the one-time owner-claim token the hub printed at start (ADR-0002), came with step 6
6. Hub as a product (H1, ADR-0025; #182): local accounts (ADR-0026), capabilities with five roles, game scope and ownership transfer (ADR-0027), an events log with notifiers (ADR-0028), the CLI as an API client (ADR-0031), the admin dashboard as a static client in the binary (ADR-0029) with operator dashboards through the hub (ADR-0030), the Compose tier, and the unplug test as the gate (#198); the telemetry store measured first (ADR-0032)
7. Operator + Agones as the fully managed driver, proven on a minimal DOKS cluster, after P5 (K1). In already: the cloud-VM driver with Counter-Strike 2 and vertical scaling at a map change, the Counter-Strike 2 adapter and the transient-server API as server leases (ADR-0003, ADR-0023)
8. Standalone agent for machines gravel does not own, and the untrusted-member test harness (cast as a fake untrusted community member)

## Explicit non-goals — do not build these

Matchmaking · player-facing allocation · billing / payment processing · anti-cheat · mod hosting · mobile app (deferred) · hub HA in v1.

## Conventions

- Version the core stats schema from day one (version field in the protobuf).
- Postgres schema migrations from day one; CRD versioning early.
- Structured logs + Prometheus metrics in every component. Metric names are a public interface (ADR-0009): a new or renamed metric goes on a dashboard in `internal/dashboards/defs.go` in the same PR (`make generate`); the drift test in that package fails otherwise.
- "Clone, one command, it's running": `make up` (ko image + podman compose) for the hub; Kind for the operator path later. Never assume a cloud cluster.
- Versions (`docs/releasing.md` "Versions", #68): before 1.0, a change that breaks a public surface (the `discord/` Go packages, the API, `hub.yaml`/`bot.yaml` keys, metric names, unit and secret names, migrations, the command lines) gets a CHANGELOG entry starting **Breaking:** and makes the next release 0.Y.0; everything else is a patch release.
- Contributor rules live in `CONTRIBUTING.md` (with `SECURITY.md`, `CODE_OF_CONDUCT.md`, `DCO`; #27): every commit is signed off (`git commit -s`), PR titles are Conventional Commits with a lower-case subject, and a PR adds a CHANGELOG line under `[Unreleased]` or carries `no-changelog`. Keep CONTRIBUTING in step when a Makefile target or a rule changes.
- `make check` before every PR; `make a11y` (axe over the pages, needs node and Chrome) when a page changes; `make hub-vm` (qemu/KVM) when the hub host's document, the stock units or `deploy/hub-vm.sh` change; `make game-vm` (local only: it pulls the 1.2 GB CS2 image) when `internal/vmdoc`, `drivers/cloudvm/templates/` or `deploy/game-vm.sh` change. Tools are pinned at the top of the Makefile and installed to `.bin/` by `make tools` (not `go tool` directives); bump a version there and, for golangci-lint, in `.github/workflows/ci.yml`. A `.templ` edit needs `make generate`; the generated Go is committed and CI fails on drift.
- The pages are API clients: a page gets its data from the hub's own Connect procedures, called in process, never from a domain service or the store (ADR-0005). Adding a page means using or adding a procedure. No inline script or style (the CSP forbids them); theme data goes through `ThemeSource`. The admin dashboard (`web/admin/`) is a client of the API like the CLI: it calls the hub over Connect with the session cookie, a page names the capability it needs in `src/nav.ts`, never a `style` prop, and `make admin-check` plus `make a11y` when it changes.
- Secrets reach containers as podman secrets (`Secret=` in quadlets, `external: true` in compose) and the config reads them through `*_file` keys. Never bind-mount a secret file (SELinux blocks it, and it leaves plaintext in a working tree).
- The owner claim: the hub mints and logs the one-time token at start while unowned, and `gravel-hub claim-token` mints one on demand on the host (stdout only, an event without the token); a logged-in user's `ClaimOwnership` (or the account page) consumes it and becomes the owner (ADR-0002, ADR-0004, ADR-0036). A hosted hub is claimed by its provisioner and handed over by ownership transfer; nothing hands a token out over the network.
- Host-configurable knobs go in the Organization settings document (`org.Settings`, one JSON on the organization row, versioned), read publicly and written by the owner through the API; never a new config key or table for a host preference (ADR-0007).
- Login: every provider is an `identity.Provider`; Goth sits behind it. Sessions and attempts are Postgres rows with hashed tokens, no signing key. State-changing routes are POSTs with the session's CSRF token behind `http.CrossOriginProtection` (ADR-0004).
- Secrets never in plaintext config or DB.
- A cloud-VM server's secrets (RCON and join passwords, the feed token, a publisher token) reach its VM over SSH from the hub, never in user-data, which the cloud keeps and anything on the instance can read (ADR-0003 as built, ADR-0020 §4).
- A file the hub puts in a game's install is a hook in the Game spec (`cloudvm.hooks`, data, no secret), pushed with the environment file and put back when it drifts; never a hand edit on the volume. CS2's `pre.sh` masks the secrets the image prints (#170).
