# ADR-0020: The hub's own host, made by the CLI through the cloud provider interface

**Status:** proposed (2026-10-11; John chose the direction the same day, accepted when he merges it) · **Changes:** who makes the machine the hub runs on, what the first `gravel` CLI commands are, what a hub host looks like; amends ADR-0003 §7 and ADR-0001's build order step 5 · **Tracked by:** #150; #35 (the provider interface it uses); hidden-token-gaming/deploy#93 (the first use)

## Context

John's path for gravel has three stages: the hub on one machine (Hidden Token Gaming ran it on a workstation from P1 to P2), the hub on a cloud instance (HTG's P3), and the Kubernetes operator for communities beyond a single machine. gravel already makes cloud machines in the design: ADR-0003 gave the hub a cloud-VM driver behind `cloud.Provider` for the VMs its servers run on, and the vertical scaling and parking that come with it. The hub's **own** host had no owner. ADR-0003 §7 left it to "an operator's infrastructure code", and ADR-0001 reserved "the hub bootstrap" for the CLI at build order step 5 without saying what that meant beyond a quadlet install.

The question John asked on 2026-10-11 was whether the provisioning gravel has for game servers should also make the hub's node. Two answers were possible.

- **The hub as a `ManagedServer` on the cloud-VM driver.** Every capability that driver has is self-harm applied to the process running it: a resize stops the hub doing the resize, parking is the hub switching itself off, and the step that recreates a dead VM from its spec runs in the hub that died. Whatever recreates a lost hub must run somewhere else.
- **The CLI makes the hub's host through the same `cloud.Provider`.** The operator's machine runs the command, so it works when there is no hub, which is exactly when it is needed: the first install and the recovery of a lost host. The seam is the one ADR-0003 built, so a second cloud added for game servers is a second cloud for the hub too.

What the clouds offer for it is the same set ADR-0003 relies on: an instance booted from a cloud-init document, a data volume that attaches to one instance at a time and moves between instances in its region, firewalls by tag. Two facts shape the document: whatever runs on the instance can read its user-data from the metadata service, unauthenticated, so the document must not carry a secret; and an instance is replaced, not repaired, when its root disk is lost, so nothing that matters may live there.

## Decision

1. **The CLI makes the hub's host; the hub is never a `ManagedServer`.** `gravel hub create` makes the hub's firewall, data volume and VM through `cloud.Provider` (DigitalOcean first, #35), and `status`, `destroy`, `allow-ssh` and `ssh` look after them. The hub keeps the game VMs (ADR-0003). Operator infrastructure code keeps the account scaffolding: the project, the tokens, a cluster.
2. **No local state.** Everything the CLI makes carries the tags `gravel-hub` and `gravel-hub:<name>` and a name derived from the hub's (`<name>-data` for the volume, `gravel-hub-<name>` for the firewall). A re-run finds what exists and makes what is missing, so a second run changes nothing and a run after a crash halfway through finishes the job. `--dry-run` says what would change and exits 3 when something would.
3. **The data volume is the runtime user's home.** The document formats the volume only if it has no filesystem and mounts it at the runtime user's home before the user is created, with a fixed uid and fixed subordinate id ranges. Everything stateful is under that home: podman's storage (images, volumes, the secret store), the user's units, the configuration. Replacing a host is `destroy` (the volume is kept unless `--delete-volume`) then `create`: the new instance mounts the same volume and comes back as it was, with the same database and the same secrets. The root disk holds only what the document recreates.
4. **No secret in user-data.** The document carries public keys, package names, unit files and configuration without secrets. The stock profile's secrets (the database password and URL, the stats pseudonym key) are generated on the host at the volume's first boot and never leave it. A secret from outside (a tunnel token) goes over SSH on standard input straight into podman's secret store.
5. **Two profiles.** `host` is the machine: an `admin` user for the OS (sudo), the runtime user `gravel` with no sudo and linger, podman, the data volume as its home, automatic security updates, and any extra packages. An operator's own configuration management installs the hub on top (HTG's Ansible does). `stock` is the host plus gravel's own units from `deploy/quadlet` and a `hub.yaml` written from flags, so one command gives a running hub: the units and configuration are installed once per volume, so an operator's later edits survive a replacement host.
6. **Before a hub exists the CLI talks to the cloud and to the host; after, only to the hub's API.** Principles 3 and 4 are about a running hub: its business rules live in its API, and the CLI uses the HTTP-JSON side of it. Making the hub's host is before any of that, so `gravel hub` speaks the cloud provider's API and SSH. It uses the operator's own `ssh` (their agent, keys and configuration), with gravel's own `known_hosts`: the key of a host gravel just made is trusted on first use, and forgotten when gravel replaces the instance, which would be wrong to do to the operator's file.
7. **The firewall admits SSH from the operator's addresses only**, and nothing else inbound: the hub reaches the world through a tunnel it dials. `allow-ssh --ssh-from-here` replaces the addresses when the operator's changes.
8. **One document, proven locally.** `gravel hub cloud-init` prints the document; `deploy/hub-vm.sh` boots it on Fedora Cloud under KVM with a second disk as the data volume, and CI's `hub-vm` job runs the drill on every change: a stock hub from nothing, ready; a new instance on the same disk, ready, with the same secrets, Postgres volume and organization.

## Amendments to earlier decisions

- **ADR-0003 §7 (ownership boundary):** "An operator's infrastructure code owns the account-level scaffolding … gravel owns the VMs it runs servers on" becomes three owners: the operator's infrastructure code owns the account scaffolding; **the gravel CLI owns the hub's own VM, its volume and firewall** (or adopts one the scaffolding made, through `cloud.Provider.Adopt`); the hub owns the VMs its servers run on.
- **ADR-0001, build order step 5:** "the `gravel` CLI as a thin HTTP-JSON client, including the hub bootstrap" now starts with `gravel hub` as described here, ahead of the rest of step 5, because a hosted hub needs it first. The cloud provider interface and its DigitalOcean implementation move from step 6 to here with it (#35); the cloud-VM driver, vertical scaling and the operator stay in step 6.

## Consequences

- New: `cmd/gravel` (released as an archive for Linux and macOS, no image), `internal/hubvm` (the document's templates and the create, status, destroy and allow-ssh steps), the `deploy` Go package (embeds the stock units), `cloud/`, `cloud/fake`, `cloud/cloudtest` and `cloud/digitalocean` (#35), `deploy/hub-vm.sh` with `make hub-vm` and the `hub-vm` CI job.
- The stock units change with it: the hub's pin moves to the current release, and `gravel-cloudflared` reads its token from its secret's file instead of the environment and is pinned by digest.
- Accepted costs: SSH host keys are trusted on first use, right after the instance is made; on DigitalOcean, cloud-init's own hostname step warns on Fedora (it runs before the system bus is up and its retry succeeds), so `create` treats cloud-init's "done with warnings" as ready and prints them; a replaced host has a new outbound address, so anything pinned to the old one (a game server's allow list) follows by hand until the hub re-pins it.
- Not decided here: the stock profile's backups, bot and observability sets (a follow-on: the bucket, its credentials over SSH), and a local-VM provider so a closet machine is a `cloud.Provider` rather than a script.
