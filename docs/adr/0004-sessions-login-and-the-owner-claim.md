# ADR-0004: Sessions, login and the owner claim

**Status:** accepted (2026-10-09) · **Changes:** how members log in, how a browser stays logged in, and who the owner claim binds to · **Tracked by:** #13

## Context

The hub's first member-visible step is a login: Discord as the primary identity, Steam linked to it, both on the `(provider, subject)` model of #5. The design chose Goth for provider login and left the mechanics open: how the browser keeps a session, how the OAuth state is bound to it, how forms are protected, and how the owner claim of ADR-0002, recorded without a user by the skeleton, becomes a real owner. Hidden Token Gaming's secrets runbook had pencilled in a "session key" for this step.

## Decision

1. **Sessions are server-side rows, and there is no signing key.** The cookie holds a random 256-bit token; Postgres holds its SHA-256, the user, an expiry and a per-session CSRF token. A copy of the table yields no usable cookie, "log out everywhere" is a delete, and the hub needs no secret for sessions, so the runbook's session key does not exist. Sessions last `auth.session_ttl` (30 days) with no idle timeout; `last_seen_at` moves at most every five minutes. Cookies are `HttpOnly`, `SameSite=Lax` and, behind HTTPS, `Secure` with the `__Host-` prefix; `auth.base_url` decides.
2. **An authentication in progress is a row too.** Starting a login or a link stores an attempt (provider, intent, the linking user, a random state, the provider's own session) and gives the browser an auth cookie naming it. The callback consumes the row before asking the provider anything, so a replayed or forged callback finds nothing; the state must match (OAuth2's `state`, or the signed `return_to` URL for OpenID, so Steam carries it too); a link must complete in the session that started it. Rows expire after `auth.attempt_ttl` (10 minutes) and are pruned.
3. **Discord logs in, Steam links.** A provider's `login` flag says whether it may register and sign a member in. Discord's default is true, Steam's false: a Steam-only account would have nothing to log in with on a hub whose community lives on Discord. A host that wants Steam login turns the flag on. Discord's scope is `identify` alone; no email is read, so the design's merge-on-shared-email path has no input in v1 and waits (a skipped test marks it).
4. **Cross-site protection is net/http's, plus a token on forms.** `http.CrossOriginProtection` refuses unsafe cross-origin browser requests by Fetch metadata (or the Origin header) in front of every handler, the API included; non-browser clients carry neither header and pass. State-changing forms also carry the session's CSRF token. The start routes are GETs on purpose: starting an attempt changes nothing a member can see, and the callback binds to the browser that holds the auth cookie.
5. **Goth, with two steps done in gravel.** Goth's Discord session exchanges the code with `oauth2.NoContext`, so the provider's HTTP client, its timeout and a test's fake endpoint are ignored; gravel does that exchange with the same `golang.org/x/oauth2` and hands the token to Goth's user fetch. Goth's Steam user fetch calls the Web API over plain `http://` with the key in the URL and fails without a key; gravel uses Goth for the OpenID verification and reads the persona over HTTPS itself, only when a key is configured. Both are upstream bugs to file; the seam stays `identity.Provider`, and any other Goth provider fits behind it.
6. **The owner claim binds to the logged-in user.** `ClaimOwnership` needs a session and records the caller as the owner; the account page carries the form, so the bootstrap is "log in with Discord, paste the token from the journal". A claim made by 0.1.0 bound nobody and granted nothing, so the migration reopens it: the hub mints a fresh token at its next start. The owner is the only privileged role for now; roles come with moderation (#18).
7. **Rate limits are per client IP for anonymous requests and per user for authenticated ones**, token buckets with a burst, 429 with `Retry-After` on pages and `resource_exhausted` on procedures, health probes exempt. Behind a reverse proxy that is the only way in, `server.client_ip_header` names the header that carries the client's address (`CF-Connecting-IP` for cloudflared); without it every request through the proxy would share one bucket.
8. **The pages are plain until #14.** `html/template`, one stylesheet, no script, a strict Content-Security-Policy. #14 restyles them with templ and htmx and keeps the routes; the flows under `/auth/` are not a page concern.

## Consequences

- Hidden Token Gaming's hub needs two new secrets (the Discord client secret, the optional Steam key) and no session key; its `hub.yaml` gains `auth` and `server.client_ip_header: CF-Connecting-IP` (deploy#46).
- The Discord application must register `<base_url>/auth/discord/callback`; Steam needs nothing registered.
- The hub's first owner logs in before claiming. An operator of a 0.1.0 hub sees it unowned again after the upgrade, with a new token in the log.
- A hub restart keeps everyone logged in; a database restore logs out whoever logged in after the backup.
