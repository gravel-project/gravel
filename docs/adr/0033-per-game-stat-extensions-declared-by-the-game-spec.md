# ADR-0033: Per-game stat extensions are declared by the Game spec

**Status:** proposed (2026-10-15; accepted when John merges #206's pull request) · **Changes:** what a match result keeps per player and what a board returns; amends ADR-0024 (the five fixed CS2 columns become extensions), ADR-0012 §6 and §7 (results' extensions are rolled up and erased like match rows) and ADR-0010 §1 (the Game spec gains `stats`) · **Decided in:** John's design session *gravel — Design Session: Hub, Spines & Dashboard* (2026-10-10 to 12), Hidden Token Gaming's roadmap re-cut (handbook D35–D36), and John's two choices on 2026-10-15 (one generic map, not fixed columns; extension totals rolled up, not lost at retention) · **Built in:** #206 · **Part of:** H1 (#182)

## Context

README's stats schema has always been "fixed common fields (kills, deaths, playtime, score, match count) + an extensions map for game-specific fields". The poll pipeline built the common half (ADR-0012). ADR-0024 then kept CS2's numbers from MatchZy as five fixed columns on `match_result_players` (assists, damage, headshot kills, MVPs, score), shown by name on the result page. A second game with stats of its own (a War Dogs build that reports captures, a PUBG match's revives) would mean a migration, a proto change and a page change each time, and the core would grow a column per game, against README principle 12 (per-game concerns live in the Game spec, never the core). The admin dashboard needs a stats page that shows any game's numbers without knowing the game.

## Decision

1. **The Game spec declares a game's own stats:** `stats.extensions`, each with a `name` (lower-case letters, digits and underscores, never a common stat: kills, deaths, kd, time, matches), a `label`, a `type` (`int`, the default, or `float`), an optional `unit`, and an `aggregate`, how a board totals a player's maps: `sum`, `avg` (per map) or `max`. At most 16. `ParseSpec` refuses an unknown aggregate or type, a bad, common or repeated name, or a missing label, like any other malformed rule. A game that declares none has the common stats only.
2. **A match result keeps a player's extensions as one JSON object of name to number** (`match_result_players.extensions`), filled with the values the result's source reports **that the server's game declares**, and nothing else. A key that is absent was not reported; a 0 is a reported zero; the API keeps the difference (proto3 `map<string, double>`). The source's own names are the keys: CS2's are MatchZy's (`matchzy.PlayerStats.Values`, with `mvp` spelt `mvps` and `2k` as `kills_2k`), and a test holds every name CS2 declares to one MatchZy reports. The five fixed columns move into the object (migration 00032) and are dropped.
3. **A board of one server or one game carries that game's extensions** (`BoardEntry.extensions`, with the columns in `GetBoardResponse.stat_extensions`): each player's results over the board's window and trusts, totalled by each extension's aggregate. The organization's board, which mixes games, carries none. The board still ranks by a common stat; extensions are columns, not a ranking (a later choice if a host asks).
4. **A result's trust is its server's when the series started** (`match_results.trust`, README principle 11), as `match_stats` rows carry theirs, so a game's board counts the same Official servers' results as its matches. The series before this take their server's trust at the migration.
5. **Extensions survive retention.** Before results past `stats.raw_retention_months` have their players anonymised (ADR-0024 as amended by #216), the same transaction adds each player's extensions to `result_stats_monthly` (a total, the maps it came from, the largest value on one map, per server, period, identity, trust and name), in the period holding the series' start, using the rollup's season-cut periods (ADR-0012 §6). A board adds those rows to the raw results, so a season's or all time's board keeps the numbers. A call whose periods miss a retiring series fails before anything changes, rather than lose its extensions.
6. **Erasure re-keys the rolled-up rows too** (ADR-0012 §7), so an erased player's totals stay counted under the token and nothing maps back.
7. **The pages render the declarations, never a game.** `ListGames` returns each game's `stat_extensions`; `GetMatchResult` returns the result's game's, and only those values; the result page and `/admin/stats` draw a column per declaration, in order, with the unit in the heading, a whole number for an `int` total or best and one decimal for a `float` or an average, and a dash read as "not reported" for an absent value. Neither knows CS2.

## Consequences

- A game's new stat is a line in its `game.yaml` and, if its source reports it under another name, a key in that source's values: no migration, proto or page change.
- **Breaking:** `MatchResultPlayer`'s fields `assists`, `damage`, `headshot_kills`, `mvps` and `score` (8 to 12) are removed and reserved; read `extensions`. `store.MatchResultPlayer` and `results.New` (which takes the declared extensions) change for a Go caller. Migration 00032 rewrites `match_result_players` and `match_results`.
- A board reads the extension totals with one more query, for its page's identities only, from the results and the rolled-up rows.
- New: `servers.Stats`/`StatExtension`, `matchzy.PlayerStats.Values`, migration 00032 (`extensions`, `match_results.trust`, `result_stats_monthly`), `store.BoardExtensions`/`OldestRetirableResult`/`ServerGame`, `stats.Boards.ServerExtensions`, the proto's `StatExtension`, `/admin/stats`.
- Not here: ranking a board by an extension, extensions from the poll (a game whose status reports more than kills and deaths), derived stats (a CS2 ADR is damage / rounds played: a formula, not a declaration), and per-game common-stat labels.
