# ADR-0029: The admin dashboard is a static client in the binary

**Status:** proposed (2026-10-13; accepted when John merges #191's pull request) · **Changes:** how the hub's operators see and run it from a browser; amends ADR-0005 §2 (a JavaScript build, for the dashboard only) and §5 (the accessibility gate covers it), and the README's web UI line · **Decided in:** John's design session *gravel — Design Session: Hub, Spines & Dashboard* (2026-10-10 to 12), handbook D35 · **Built in steps:** #191 (this scaffold), then its pages: #192 (the fleet), #193 (events and alarms), H1-18 to H1-24 · **Part of:** H1 (#182), the unplug test (ADR-0025)

## Context

The unplug test (ADR-0025) asks that a hub with no Discord show its owner what is wrong and let them act. The member pages (templ and htmx, ADR-0005) are built for members reading boards and servers, one request per action, and work without JavaScript. An operator's view is different: a fleet that changes every few seconds, an events feed followed by cursor, forms over the whole Organization settings, per-server actions gated by capability. Doing that in htmx means server-rendered fragments for every widget and a poll per fragment; the design session chose a single-page client over the same API instead, with the member pages left as they are.

## Decision

1. **A React and TypeScript single-page app in `web/admin/`**, built with Vite (React 19, TypeScript strict, Tailwind 4, TanStack Query, wouter for routes). The member pages stay templ and htmx; nothing a member needs moves into the dashboard.
2. **Its clients are generated from `proto/`.** `buf.gen.ts.yaml` runs protobuf-es as a pinned remote plugin (`buf.build/bufbuild/es`, the version `package.json` pins for `@bufbuild/protobuf`) into `web/admin/src/gen/`, committed, regenerated by `make generate` and checked for drift like `gen/`. The dashboard calls the hub with Connect-Web over HTTP-JSON, so it can do only what the API allows, exactly as the pages (ADR-0005 §1) and the CLI.
3. **It signs in with the session cookie, not a token.** Calls go to the same origin with the cookie the login set; `http.CrossOriginProtection` (Fetch metadata, then Origin) refuses a cross-site call that changes anything, as it does for the pages' forms. No bearer token is held in JavaScript. The gate is `GetMe`: `unauthenticated` sends the browser to `/login?return_to=` the page it was on; the login and the account stay the hub's own pages.
4. **It is embedded in the binary and served at `/admin`.** `make admin` builds into `internal/web/admin/dist/` (ignored by git but for a `.gitkeep`), which `internal/web/admin` embeds. `GET /admin` and every path under it answer the index (the app routes in the browser); `assets/` holds files named by their content hash, cached for a year as immutable, and a missing one is a 404. The index is never cached. A binary built without the bundle (a bare `go build`) answers 503 "the admin dashboard was not built" at `/admin`, logs that at start, and serves everything else. No member page route lies under `/admin`; a test lists them.
5. **The pages' Content-Security-Policy, unchanged.** Nothing is inlined: no inline script or style element, no `style` attribute (an ESLint rule forbids the `style` prop), no event handler attribute, no `javascript:` URL, no `data:` asset; Vite's module-preload polyfill is off. A Go test reads the embedded bundle for each of these.
6. **The brand tokens, under the host's theme.** The bundle carries `internal/web/static/brand/tokens.css` (the `--gravel-*` tokens) and Tailwind's colours map onto them, under the host's `/theme.css` where it sets a token, so the dashboard follows the Organization settings' theme and the viewer's light or dark setting like the pages.
7. **It polls; nothing is pushed.** Every query refetches every 5 seconds while the tab is visible and stops in a background tab (ADR-0028 §6). A refusal is not retried.
8. **The nav follows capabilities.** A page names the capability its procedures check and, where a game-scoped grant brings it, the roles that do (ADR-0027 §4); a member sees what they can use. The API still decides every call.
9. **It is checked like the pages.** CI's `admin` job lints, typechecks, runs the tests (each route rendered over fake services through Connect's router transport, with axe) and builds, then runs the Go bundle check against the bundle it built. `make a11y` scans `/admin` in Chrome too, after checking that the page rendered.

## Consequences

- Building the hub needs Node.js (the version in `web/admin/.nvmrc`): `make build`, `make image`, CI's jobs that build the hub, the publish job and goreleaser's hook build the bundle first. `go build` and `go test` alone still work; that binary serves the 503.
- Two front-end stacks: templ and htmx for members, React for operators. A page belongs to one of them; when the dashboard grows a page that replaces a member page (`/members`, H1-19), the member page redirects to it.
- The bundle is about 125 kB gzipped, most of it React and the API's descriptors; it loads once and is cached until the next build.
- Serving the dashboard from a CDN or another origin needs public clients (#161) and is out of H1.

Amends [ADR-0005](0005-the-web-ui-is-an-api-client.md): §2's "no JavaScript build" holds for the member pages; the admin dashboard has one. §5's gate covers `/admin`.
