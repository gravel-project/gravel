# ADR-0010: External-reachable drivers are capability-driven, and a server is a hub resource

**Status:** proposed (2026-10-09) · **Changes:** how the hub knows a server exists, how a driver is written against a game whose API changes, how moderation is recorded, what the hub runs in the background · **Tracked by:** #24 and #16; #8 (the bands it enforces), #18 (the pages that render it); hidden-token-gaming/deploy#137 (the first deployment), htg#31 and htg#57 (the first consumers), wardogs-server#12 and #13

## Context

The design's `ManagedServer` records a server that exists somewhere and a driver controls it; the external-reachable driver covers a server we can reach over RCON or SSH but do not run (README, "Representation vs execution"). Hidden Token Gaming's first game is one of those: a War Dogs server at QONZER, reachable only over a plain-HTTP bearer RCON API with 29 routes, a whole-document config and a push kill feed. None of what it needs exists in the hub at 0.6.0: no `Game` or `ManagedServer` row, no server procedure, no background job but the session prune loop, no secret beyond the three in `hub.yaml`.

War Dogs is in Early Access and changes its API every few weeks (plan G10, #24): CL-501228 removed eight write routes and folded them into the config document, CL-507060 added `AllowedHosts` and cut server internals from responses, route parameter names differ between builds and hosts, and Season 02 lands on 2026-10-15. A driver that hard-codes a route list, a key list or the catalog is stale on the next patch. The server also sets the rules a client must keep: 600 requests a minute per address, a 64 KiB body, a `Retry-After` on a 429, and an undocumented throttle that answers 429 on every protected route after three requests with a bad token; `GET /v1/config` returns the RCON password in clear; the host restarts the server daily and announces nothing. John's rule of 2026-10-08: embrace that in the driver.

## Decision

1. **`Game` and `ManagedServer` are rows behind a `ServerService`, applied from a manifest.** Migration 6 adds `games` (the spec: id, name, the identity provider its players are keyed by, the publisher bands from #8, the layout data #18 renders) and `managed_servers` (id, name, game, driver, location, endpoint, the credential's file, the poll interval, trust, and a `seeding` section with the knobs hidden-token-gaming/htg#32 reads). gravel ships the War Dogs spec as a file in `games/wardogs/`; a manifest names it and may tighten its bands, never loosen them. Reads are public for what carries no personal data (`ListGames`, `ListServers`, `GetServerStatus`); the player list is a member's or an app's with `servers:read`; writes are the owner's. Until the `gravel` CLI exists, `gravel-hub servers export|apply|check` are the settings commands' siblings (ADR-0007 §4), so a deployment commits `servers.yaml` and applies it on converge. The resource holds no credential: the manifest names a file (`/run/secrets/…`), the hub reads it at start and at apply, logs its source and never its value, and stores none of it, the rule `hub.yaml`'s secrets already follow.

2. **A driver discovers what it can do, and the hub shows only that.** `drivers.ExternalReachable` is the Go interface: `Capabilities`, `Status`, `Players`, the moderation calls, `Config` (get, plan, apply) and `Build`. Its capabilities flag is a set computed from the server, not a constant: the War Dogs driver reads `GET /v1/capabilities` at start and on every build change, matches routes by shape (method and path segments, a `{parameter}` wherever one stands, so `{id}` and `{steamId}` are the same route), and reports a capability absent when its route is missing, which the pages and the bot render as "not available", never as an error. Parsing is tolerant: unknown fields are ignored, unknown enum values are kept as strings, optional fields are optional. The client library in `games/wardogs/` has no gravel imports (the cut rule, enforced by depguard); `drivers/wardogs/` adapts it.

3. **The hub runs drivers as supervised jobs.** The hub gains a job runner, the prune loop generalised: named jobs with `gravel_hub_jobs_total{job,result}`, a failure logged and retried with backoff, never fatal, because a poll that fails is a state the UI shows, not a reason to stop serving. One poll job per server reads status and players at the server's interval (15 s by default, two requests) and keeps the last observation in memory with `observed_at`; two misses mark the server unreachable, the next success clears it with no gap in the API. One token per server, never a retry on a 401 (the throttle), `Retry-After` honoured on a 429, a budget well inside the server's limit. Population samples go to the stats store when #17 exists (seeding minutes, recaps); until then the observation is the only state.

4. **The build watcher is the capabilities poll on a slower clock.** Every 60 s the public build string is read; on a change the driver re-reads capabilities, the catalog and the config schema (`sections[]`), diffs them against the set it holds, logs the diff, increments `gravel_driver_build_changes_total` and sets `gravel_driver_build_info{server,build}`, and refreshes its capability set. A Prometheus rule on those names is the alert (hidden-token-gaming/deploy#50). Updating the recorded fixtures is a human step: `gravel-hub wardogs record` writes `games/wardogs/testdata/<build>/` (capabilities, catalog, schema, sample reads, the config document redacted) from the live server's read-only routes, one token and no retry, and a pull request commits them. CI runs the driver against every recorded build; `go test -tags live` runs the same contract tests against a real server, read-only, on demand.

5. **Moderation goes through the hub and leaves an audit row.** `KickPlayer`, `BanPlayer`, `UnbanPlayer`, `MessagePlayer`, `Broadcast` and `MovePlayer` are procedures behind `servers:moderate` (an app) or the owner (the moderator role comes with #18); each calls the driver and writes `audit_log` (migration 6: when, who, server, action, target, reason, outcome, request id), a table nothing updates or deletes. A ban is keyed by SteamID64 with a reason and an issuer: online through `POST /v1/bans`, offline as a `DefaultBannedPlayerIds` line in the config document, because the server refuses to ban a player who is not on. The bot's `/wd` commands (htg#57) call the same procedures with the bot's credential, so one log holds both surfaces.

6. **Config is the server's schema, then the spec's bands, then `If-Match`.** `PlanServerConfig` and `ApplyServerConfig` (owner or `servers:configure`) take the redacted desired document a deployment keeps in its own repository (wardogs-server#12): the driver merges the sections it owns from its secrets (the RCON block, the feed's `Url` and `Token`), checks the bands before anything leaves the hub, validates with the server (`POST /v1/config/validate`) and applies with `If-Match` on the revision it planned against, refusing on a 412. The result carries the server's `outcomes[]` (applied, next match, next restart, pending), `shadowed[]`, `stripped[]` and `warnings[]` per section, so a next-restart key reads as pending until the host's daily restart. The document is CRLF on the wire; the hub compares normalised and sends CRLF.

## Consequences

- Migration 6 is additive (`games`, `managed_servers`, `audit_log`), three scopes join `identity:read` (`servers:read`, `servers:moderate`, `servers:configure`) and `hub.yaml` gains nothing: patch releases under the 0.x rule, 0.6.1 on, one per PR in the order recorder and fixtures → client and capabilities → resources, manifest, poll and API → moderation and the audit log → config and the watcher.
- The hub has a job runner now; later drivers and the ingest route's reconciliation (#4) use it. Every new metric lands on the hub dashboard in the same PR (ADR-0009).
- Hidden Token Gaming registers its server with one deploy PR (deploy#137: the manifest, a twelfth secret, the role applying `servers.yaml` on converge) and retires its UptimeRobot build monitor once the watcher's alert reaches its alerts channel. The live card (htg#31) reads `GetServerStatus` and never RCON.
- Season 02 (wardogs-server#13) is the first re-record. The feed's per-event format is confirmed from the S1 captures (deploy#49) before #4's parser is final; nothing here depends on it.
- The cloud-VM driver (ADR-0003) and the fully managed driver implement the same `Status`, `Players` and moderation surface over their own channels; the capabilities set is how each says what it lacks.

## Amendments

- **2026-10-10, as built.** The recorder and the client shipped as one release (0.6.1, #82): the recorder is the client's first user. Migration 6 holds `games` and `managed_servers` only; `audit_log` comes with the moderation procedures that write it, as migration 7, and `servers:moderate` and `servers:configure` with the procedures they admit, so no table or scope exists before what uses it. A server taken out of `servers.yaml` is marked removed, not deleted, so the audit log and stats keep their target. The public status carries a `state` word (`ok`, `unreachable`, `credential_refused`, …) and never a failure's text, which can name the control address. The Game spec's layout data waits for #18, its first reader.
- **2026-10-10, moderation as built (0.6.3).** The procedures are a service of their own, `ModerationService`, beside the public reads of `ServerService`, with `ListServerBans` and `ListAuditLog` (keyset pages, newest first) so a moderator can see what to unban and what was done. `audit_log` is append-only with one exception: the row is written *before* the driver is called (no row, no call) and its outcome is filled in once afterwards; a trigger refuses every other `UPDATE`, every `DELETE` and `TRUNCATE`. The outcome is a word, like the public state, never error text. An app may name the person it acts for (`on_behalf_of`, a provider identity as the app asserts it), so a bot's commands record the Discord moderator; a user acts as themselves. A kick and a ban need a reason. `MovePlayer` takes `respawn` (a kill after the move, as War Dogs' console does). Calls go through the monitor's driver for the server, so a server has one client and one token. A ban of an offline player (a `DefaultBannedPlayerIds` line) waits for the configuration step, because it is a configuration edit and the deployment's configuration-as-code (wardogs-server#12) must agree on who owns that list; until then `BanPlayer` answers `not_found` for a player who is not on. The ban model in the design (scope, expiry, re-push when a banned identity shows up) needs a hub-owned bans table and waits for the stats stream. Erasure (principle 8, not built) will be the trigger's second exception: a re-key of the subject columns, nothing else.
- **2026-10-10, the watcher as built (0.6.4) and the last step split.** The build watcher ships alone, ahead of configuration, so it watches Season 02 (2026-10-15). It is a per-server job (`server_build`, every minute, backoff to 5 minutes) that reads the build from the public capabilities route and, on a change, the capabilities again (the poll read them once at its first success before). It does not re-read the catalog or `sections[]`: the first needs no hub reader yet and the second is the configuration step's; the driver logs the route diff, which is what a human re-recording the fixtures needs. Metrics carry the `game` label like the other server metrics: `gravel_driver_build_info{server,game,build}` and `gravel_driver_build_changes_total{server,game}`. gravel ships no alert rule (a host's Prometheus owns its rules); the alert is an increase of the counter. Configuration plan and apply, with the hub-owned `DefaultBannedPlayerIds` (John, 2026-10-10: the deployment's document leaves the key out and the driver merges the hub's list, as it does the secret sections), follow as 0.6.5.
