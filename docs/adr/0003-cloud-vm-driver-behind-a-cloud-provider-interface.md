# ADR-0003: A cloud-VM driver behind a cloud provider interface, DigitalOcean first

**Status:** accepted (John, 2026-10-08) · **Changes:** adds a fourth lifecycle driver to the 2026-09-25 design's three, and the seam under it; amends build order step 6 · **Tracked by:** #34

## Context

Hidden Token Gaming decided on 2026-10-08 (its D22 and D23) that its Kubernetes test environment is a DigitalOcean Kubernetes cluster, minimal and with no game servers on it until the cluster is scaled; that its Counter-Strike 2 test server runs on a Droplet; that gravel must size that Droplet with its population, moving from a 10-player size to a 20-player size at a map change as the server fills; and that the DigitalOcean support must be shaped so AWS, Azure and Google Cloud can follow behind the same interface.

The design has three lifecycle drivers and none of them owns a host. The fully managed driver owns pods; Agones places them on nodes somebody else provisioned. The external-reachable driver owns nothing: it reads and commands a server over RCON or SSH. The externally referenced driver only lists. The standalone agent runs processes on a machine its member provisioned and may not change that machine (principle 8). The one Droplet in the design is the untrusted-member test harness, which is about trust, not lifecycle. A server whose machine gravel itself creates, sizes and destroys is a gap, and it is the common case for a small community: one game, one VM, sized to the room.

What the clouds offer for it has one shape, verified for DigitalOcean on 2026-10-08 and known for the others. An instance is resized while stopped (DigitalOcean's API stops it for you; EC2's `ModifyInstanceAttribute` and GCE's `setMachineType` want a stopped instance, Azure resizes with a restart or a deallocation). A change of CPU and memory is reversible; a change of the root disk is not. Data disks are separate resources that attach to one instance at a time and move between instances in the same datacenter. A floating address moves between instances. Instances boot from a user-data document, firewalls are rules by tag, and billing is by the hour or the second. DigitalOcean adds three facts that decide the shape: the target plan's disk must be at least the Droplet's; downtime grows with the used root disk (the docs say about a minute per GB, because the Droplet may move hypervisor); and a powered-off Droplet bills in full.

Go has no multi-cloud compute SDK (gocloud.dev covers blob, pubsub, secrets, docstore and runtime variables, not instances). Provisioners (OpenTofu, Pulumi, Cluster API, Crossplane) are declarative and reconcile on their own clock; a decision taken at a map change needs an API client that acts now and reports an operation. Each vendor's SDK is solid (godo for DigitalOcean, aws-sdk-go-v2, azure-sdk-for-go, cloud.google.com/go/compute); what is missing is the seam.

## Decision

1. **A fourth driver: cloud-VM.** gravel creates, sizes, powers, parks and destroys a single-tenant virtual machine for one `ManagedServer` through a cloud provider interface. The game runs on the VM under systemd, installed by a cloud-init document rendered from the `Game` spec, in the container flavor (podman and the game's image) or the native flavor the design already gives the local-execution path. gravel controls the game over the game's own channels, as the external-reachable driver does: RCON, and a log push to the hub's ingest endpoint. A machine gravel owns needs no agent and no SPIRE; the standalone agent stays the path for machines gravel does not own, and build order step 7 keeps that purpose.

2. **`cloud.Provider` is the seam**, in domain terms (principle 2): regions and sizes (vCPU, memory, root disk, hourly price, family, dedicated CPU, whether a stopped instance bills); create, get, delete, start, stop, resize; volumes (create, attach, detach); addresses (allocate, assign); firewall rules; adopt an instance made outside gravel. Every mutating call returns an operation the driver waits on with a deadline. Each provider publishes its resize constraints as data (`CanResize(from, to)`), so the validation of a ladder is generic. `cloud/digitalocean` (godo) is the first implementation and `cloud/fake` the test double; AWS, Azure and Google Cloud are later packages against the same interface and the same conformance suite, written when somebody needs one and not before (#35).

3. **Game data on a detachable volume; the root disk minimal and fixed; a resize never touches disk.** The root disk holds the operating system only and is created at the smallest size the ladder allows. The game's install lives on a volume (a 60 GB Counter-Strike 2 install on a 100 GiB volume), which keeps a resize to minutes instead of an hour, keeps every plan family reachable, and lets a replacement VM take the install over. The rule is the same at every cloud (an EBS volume, a managed data disk, a persistent disk).

4. **Vertical scaling is a policy of the driver** (#37): a ladder of tiers (size, player slots, per-tier game config) declared in the Game spec and overridable per server; signals from the server's own population, its trend, and the expected population a first-party app announces; a decision taken continuously and executed only at a boundary the game announces (a map change, a match end, an empty server), with hysteresis, a cooldown, a chat warning, and a manual pin that wins. Two strategies behind one interface: in-place (stop, resize, start) first; replace (the next tier booted ahead, the volume and the address moved at the boundary) later. Every decision is an audit entry and a metric, and the server page shows the tier and the cost.

5. **Parking is provider-dependent, and the driver knows it.** An empty server past its idle window is parked: stopped where a stopped instance is free, destroyed with its volume and address kept where it is not (DigitalOcean). Unparking recreates it from the same spec. This is the transient-server lifecycle (#20) applied to a VM.

6. **The Kubernetes test environment is a minimal DOKS cluster with no game servers until it scales.** Agones and the operator run there, so the operator path (#21) is proven on a real cluster; Kind stays the CI target. The operator stays cluster-agnostic; DOKS specifics (the managed firewall that must admit UDP 7000–8000, nodes with public addresses) belong to the deployment repository, not here.

7. **Ownership boundary.** An operator's infrastructure code (HTG's OpenTofu) owns the account-level scaffolding: project, network, SSH key, firewall templates, the Kubernetes cluster, the tokens. gravel owns the VMs it runs servers on, with their volumes and addresses. `Adopt` lets a VM the scaffolding made first (HTG's Counter-Strike 2 test Droplet) come under gravel's control without a rebuild.

## Consequences

- The driver taxonomy reads: fully managed (Agones) · **cloud-VM (a VM gravel owns, through a cloud provider)** · external-reachable (RCON, SSH) · externally referenced. The capabilities flag gains `resize` and `park`. README and CLAUDE.md say so.
- New packages: `cloud/` (the interface, the fake, the conformance suite), `cloud/digitalocean/`, `drivers/cloudvm/`, and `games/cs2/` (RCON and log parsing, no gravel imports, per the layout rule). Nothing outside `cloud/` imports a vendor SDK.
- The provider token is a hub secret. The RCON and server passwords are hub secrets written into cloud-init once. The hub's egress address is pinned in the VM's firewall for RCON and SSH, and the driver re-pins it when it changes; a hub behind a changing address accepts that RCON is reachable from one address at a time.
- Accepted costs: an in-place resize disconnects every player for two to five minutes, which is why it happens only at a boundary; a DigitalOcean Droplet has standard, not game-grade, DDoS protection; the replace strategy doubles the cost for the minutes both VMs exist; the API's rate limit (DigitalOcean: 5,000 requests per hour per token) bounds the polling budget.
- Recovery: every lifecycle step is a recorded operation in Postgres, so a hub that restarts mid-resize resumes or restores the old tier; a failed resize restarts the server at the old tier and alerts. Tags and names make a half-made VM findable, so a retry is idempotent.
- Build order step 6 becomes: the operator and Agones as the fully managed driver, proven on a minimal DOKS cluster; the cloud provider interface and the DigitalOcean implementation; the cloud-VM driver with Counter-Strike 2 and its vertical scaling policy; the Counter-Strike 2 adapter; the transient-server API (#21, #9, #35, #36, #37, #20). Step 7 is unchanged in purpose: the standalone agent for machines gravel does not own, and the untrusted-member harness, which may now run on a VM the cloud-VM driver makes.
- Not decided here: whether HTG's hub moves to the DOKS cluster or to a Droplet when it leaves earth (HTG's S9, hidden-token-gaming/deploy#41), and the per-game defaults of the ladder, which the first measured resize round trip sets (hidden-token-gaming/deploy#110).
