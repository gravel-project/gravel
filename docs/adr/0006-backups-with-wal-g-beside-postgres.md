# ADR-0006: Backups with WAL-G beside Postgres

**Status:** accepted (2026-10-09) · **Changes:** how the hub's database is backed up and restored, and what the hub watches of it · **Tracked by:** #28

## Context

ADR-0001 moved backups from an operator (CloudNativePG) to the hub: base backups plus continuous WAL archiving to object storage, and a scripted, timed restore to a wall-clock point. The hub is the single point of no return (identities, the linked-account graph, the audit logs and the stats history cannot be rebuilt from game servers), and on Hidden Token Gaming it sits on one workstation disk. The issue asked for an existing tool, pgBackRest or WAL-G, rather than anything hand-rolled, and for CI to exercise backup and restore.

## Decision

1. **WAL-G, inside the Postgres image.** `ghcr.io/gravel-project/gravel-postgres` is the official Postgres 17 image plus the WAL-G binary, fetched at build time from its release and checked against the published SHA-256 for each architecture (`deploy/postgres/Containerfile`). Postgres runs with `archive_mode=on`, `archive_command='wal-g wal-push %p'` and `archive_timeout=60`, so every WAL segment reaches the archive within a minute of being written, and a segment counts as archived only once the upload succeeded. WAL-G over pgBackRest because it is one static binary that speaks S3 (Cloudflare R2 and MinIO-likes included) with no configuration file, which is what one container of one database needs; pgBackRest's repository model and parallelism earn their place with many clusters. The image is versioned and signed with gravel's releases and pinned by digest, like the hub.
2. **A nightly base backup as a oneshot unit of the same image.** `gravel-backup.timer` runs `gravel-backup`: `wal-g backup-push` on the data volume mounted read-only (WAL-G reads the files; it connects to Postgres only to mark the backup's bounds), then `wal-g delete retain FULL 30`, then a status file. The job shares WAL-G's settings with Postgres and reads its database password from a pgpass secret mounted with mode 0400 (libpq refuses a readable one).
3. **The hub watches, it does not back up.** `backup.status_file` names the status file (`gravel-backup.volume`, mounted read-only in the hub); the hub turns it into `gravel_backup_last_success_timestamp_seconds`, `gravel_backup_last_run_timestamp_seconds` and `gravel_backup_last_run_ok`, and reads `pg_stat_archiver` at every scrape for `gravel_wal_archived_total`, `gravel_wal_last_archived_timestamp_seconds`, `gravel_wal_archive_failed_total` and `gravel_wal_last_failed_timestamp_seconds`. Ages are left to the alert rules (`time() - …`), the Prometheus way; the two `_readable` gauges say when a metric is missing because the source could not be read rather than because nothing happened. The hub holds no bucket credential.
4. **Restore is a script, not a hub command.** `gravel-restore --to <RFC 3339>` (or `--latest`) runs in a container of the same image against an empty data volume: `wal-g backup-fetch`, then `restore_command = 'wal-g wal-fetch %f %p'`, the target time and `recovery.signal`, so the next Postgres start replays WAL to the point and promotes. It refuses a non-empty directory. The issue sketched `gravel-hub restore`; stopping Postgres, wiping a volume and starting it again are an operator's steps with podman, not the hub's, and the hub's readiness confirms the schema afterwards.
5. **The drill is CI.** `make backup-drill` (`deploy/backup-drill.sh`) starts a local S3 store (versitygw, a directory per bucket; MinIO's images are no longer published), a Postgres from the image archiving into it, writes rows, takes a base backup, writes more, notes a point in time from the database's own clock, writes more, forces a segment switch, destroys the database, restores to the point into a fresh volume, and checks that exactly the rows before the point came back and that the hub's migrations are current, timing the restore. CI runs it on every pull request.
6. **Backups are opt-in per deployment.** The base quadlet units run plain Postgres; `deploy/quadlet/backup/` holds the drop-ins that switch the image and turn archiving on, the backup unit, its timer and its volume, installed by `make quadlet-install-backup` after the bucket lines are edited and the credentials secret exists. The development stack always archives, into its local store, so `make up` mirrors production and `make backup` takes a base backup.

## Consequences

- Hidden Token Gaming's deploy#43 is now a bucket, two secrets (the credentials file, the pgpass line), the drop-ins with its endpoint, the timer, `backup.status_file` in `hub.yaml`, alert rules on the four timestamps, and the drill run on earth with its time in the README.
- Every WAL segment goes to object storage; at the hub's write rate that is a few segments an hour at idle (`archive_timeout`) and a 16 MiB object each, retained with the base backups that need them.
- A restore brings back everything up to the target; sessions issued after it are gone, and so is a claim made after it (the hub mints a token again if the restored organization is unowned).
- The image build adds a Containerfile and a multi-arch build to the release workflow beside goreleaser.
