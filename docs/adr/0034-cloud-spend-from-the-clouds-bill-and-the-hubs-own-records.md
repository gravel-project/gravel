# ADR-0034: Cloud spend from the cloud's bill and the hub's own records

**Status:** accepted (2026-10-15, John; built in #207, amended by the first real preview below) · **Changes:** adds an optional cost reader beside `cloud.Provider` (extends ADR-0003) and what an operator sees of money (extends ADR-0029's dashboard) · **Decided in:** John's design session *gravel — Design Session: Hub, Spines & Dashboard* (2026-10-10 to 12), Hidden Token Gaming's roadmap re-cut (handbook D35–D36), and John's choice on 2026-10-15 (both the cloud's bill and the hub's estimate) · **Built in:** #207 · **Part of:** H1 (#182)

## Context

A host running servers on a cloud wants to know what it costs this month, what for, and where the month will end. The hub already knows part of it: each cloud-VM server's runs at the hourly price recorded when the run began (ADR-0003 as amended), shown per server as "this month". It does not know what it didn't make or record: a volume or an address that bills while a server is parked, snapshots, bandwidth over the allowance, the hub's own Droplet, anything made by hand. The cloud does: DigitalOcean's invoice preview, generated daily, has each resource's month-to-date amount with its project. But it needs the token's `billing:read` scope, and a billing token is **team-wide**: on a team shared with other projects (Hidden Token Gaming's lives in John's personal team) it can read every project's bill.

## Decision

1. **An optional cost reader, beside the provider:** `cloud.Coster` (`MonthToDate(ctx) (Bill, error)`), the cloud's own bill for this month so far, line by line, for the provider's project, and the lines the cloud puts in no project or its default one, marked unassigned, which the hub keeps only when one of its servers is their cause (§3): DigitalOcean bills volume snapshots in the default project and a Droplet's public IPv4 in none, whatever project the resource is in (seen on Hidden Token Gaming's first preview, 2026-10-15). Never another named project's lines. A provider implements it or not; the hub finds it by type assertion (the drivers' optional-interface pattern), so no `Provider` implementer changes. A token without the scope answers `cloud.ErrForbidden`. A `BillLine` carries the resource's id and name where the cloud gives them, the product, a kind (`compute`, `storage`, `network`, `other`), the description, and USD. DigitalOcean's comes from the invoice preview (`GET /v2/customers/my/invoices/preview`), keeps the items whose `project_name` is the location's project (and the unassigned ones), maps the product to a kind by keyword (Droplets compute; volumes, snapshots and backups storage; IPs, bandwidth and load balancers network), takes the name from a description's "name (detail)" after any "Kind - " prefix, and the id from a `do:droplet:<id>` URN; a line in no project whose resource is one of the project's lines (a Droplet's public IPv4) is the project's.
2. **The hub keeps a snapshot a day** (`cloud_bills`, `cloud_bill_lines`): the `cloud_spend` job (every 6 hours, the day's snapshot replaced each time) reads each cloud location's bill and stores its lines in the organization's timezone's day. The cloud's preview is the month so far up to its last nightly run, so the newest snapshot is the month to date and the difference between two days' is one day's spend. Nothing personal is in it; it is kept.
3. **Each line has a cause:** the server whose resource it is, by the cloud's resource id (the host's instance or volume) or, because parking makes a new instance each time, by name (the instance is the server's id, the volume `<id>-data`, a snapshot `<id>-data-…`, ADR-0003's names). Anything else (the hub's own host, something made by hand) is shown by its name, uncaused.
4. **The hub's estimate stands beside it, always:** the compute each cloud-VM server's runs cost at their recorded prices, day by day, from the host events. It needs no scope and works on any cloud, but it is a floor: compute only, and only what the hub ran. Where a location's bill is readable, the bill is the figure; where not, the estimate is, and the page says which and why.
5. **A projection, said as one:** the month to date plus the average day of the last seven whole days (fewer at the month's start, the elapsed fraction of the first day on the 1st) times the days left. On the bill, "billing lags a day": the preview stops at its last nightly run, which the page shows as "as of".
6. **Who sees it:** `ServerHostService.GetSpend{month}` needs `servers:provision` held everywhere (the capability for what changes spend; admins and the owner). `/admin/spend` shows the month to date and the projection, the days, the servers by kind, and the uncaused lines. With no cloud location it says so.

## Consequences

- A host shares a team-wide bill with the hub when they give its token `billing:read`; the hub stores only its project's lines. Without the scope everything works on the estimate.
- DigitalOcean's product names and description format are not documented as stable; the kind mapping and the name parsing are best effort, a line that matches nothing is `other` and uncaused, never dropped.
- One more API call per cloud location every 6 hours, paged at 200 items.
- New: `cloud.Coster`, `cloud.Bill`, `cloud.ErrForbidden`, the fake's and DigitalOcean's implementations and the emulator's preview route, migration 00033, `internal/spend`, the `cloud_spend` job, `GetSpend`, `/admin/spend`.
- Not here: past months' finished invoices (the snapshots cover the months the hub ran through), per-tenant spend for GRVL (the causes are the seam), budgets and alerts on spend (a notifier rule over this, later), and non-cloud costs (R2, domains).
